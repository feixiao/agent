## 一、 系统工程定位与架构本体论

## 二、 破除四大物理鸿沟的系统级工程解法

`FastAvatar` 的架构设计精准映射了通用 Harness 走向端侧语音助手时面临的核心物理挑战：

### 1. 物理声学自激解法：硬件级 AEC 与全双工状态机
* **问题**：助手扬声器播报的声音被麦克风二次采集，导致自问自答和自我唤醒。
* **Harness 解法**：
  * **声学回声消除（AEC, Acoustic Echo Cancellation）**：在系统音频输入端挂载物理参考回路（macOS 下结合 CoreAudio / Web Audio AEC，Android 下启用系统级 Voice Communication 模式），实时消除扬声器播放信号。
  * **四态有限状态机（FSM）严格互斥**：
    $$\text{IDLE} \longleftrightarrow \text{LISTENING} \longleftrightarrow \text{THINKING} \longleftrightarrow \text{SPEAKING}$$
    在 `SPEAKING` 状态下仅开启针对用户人声特征的高置信度打断检测，抑制低能量环境底噪与扬声器漏音。

### 2. 听觉异步撕裂与毫秒级打断：Barge-in $\le 50\text{ms}$ 与 KV Cache 截断
* **问题**：大模型一秒吐出 30 个 Token，而人类语速 1 秒只能读 4~5 个字。用户听到第 2 秒插话打断时，模型早已经把整段文字生成完毕，导致上下文与用户认知脱节。
* **Harness 解法**：
  * **端侧两级瞬断（Edge-Kill）**：用户开嗓（VAD 判定语音起始）耗时 $\le 50\text{ms}$，端侧立即执行两步：
    1. 掐断扬声器并清空待播切句环形缓冲区（RingBuffer）；
    2. 丢弃当前未播报的文本切片。
  * **云端协程强杀与回滚（Cloud Cancellation）**：端侧通过长连接向云端下发取消信号，云端网关立即触发 `context.CancelFunc()` 强杀 LLM 推理协程，截断并回滚上下文历史中未被用户听到的多余 Token，保证多轮上下文与物理现实绝对一致。

### 3. 首字延迟（TTFT）与端侧统一发声：首句微切与 Unified Edge TTS
* **问题**：若等待整句或整个段落生成完再送入 TTS，首字延迟会飙升至 2~3 秒，产生令人窒息的死寂；若端侧小模型用本地音色、云端大模型返回云端音频流，用户会听到两种完全割裂的声音。
* **Harness 解法**：
  * **流式微切分器（Streaming Sentence Chunker）**：Harness 在文本流中设置首句极小字数阈值（**首句仅需 4~6 个字**，检测到逗号、顿号或短停顿立即断句送入 TTS 预热合成），后续句子按标点自然断句，使端到端发音延迟（TTFT）压缩至 $\le 150\text{ms}$。
  * **端侧统一发声（Unified Edge TTS）**：无论是本地快环还是云端慢环，云端与端侧**全链路只传文本 Token 流**，最终全部在端侧交由同一个轻量级离线 TTS 引擎（如 Sherpa-ONNX）统一渲染发音。既根除了音色割裂，又省去了 99% 的音频流服务器带宽成本。

### 4. 移动端功耗墙与意图短路：C++ 微内核与单字防误触
* **问题**：手机发热限频、电池电量敏感；高频控制指令上云延迟高且耗电。
* **Harness 解法**：
  * **纳秒级查表意图仲裁（`IntentArbiter`）**：采用 C++ 原生实现，利用 `std::string_view` 和零堆内存分配（Zero Allocation），在 $\le 10\mu s$ 内完成常用动作与设备控制指令的嗅探。
  * **全词精准防误触**：单汉字强控制指令（如“停”、“走”）采用全词对齐匹配，杜绝“暂停播放”被“停”粗暴误拦截。
  * **多轮对话状态追踪（DST, Dialogue State Tracking）**：意图路由器感知上一轮的执行环境；若上一轮处于云端代码推演，后续“第三行呢”等短代词追问强制继承云端，防止盲目短路回本地。

## 三、 FastAvatar 跨端工程模块与代码映射

`FastAvatar` 展现了极高标准的工程实现分层，符合“C++ 原生微内核 + 跨平台薄宿主”的架构原则：

| 模块目录 / 文件 | 运行环境 | 对应 Harness 职责 | 核心实现机制 |
| :--- | :--- | :--- | :--- |
| `core/` (`libaudio_agent`) | 跨平台 C++17 原生库 | **语音声学与意图仲裁底盘** | 麦克风 PCM 帧采集、LockFree 环形缓冲、$\le 50\text{ms}$ 打断、纳秒级 `IntentArbiter`、动作元语抽象 |
| `internal/dispatcher/` | macOS (Go) | **端云意图分流与状态路由** | 多轮状态追踪（DST）、规避字数阈值粗暴判断、云端超时 50ms 自动平滑降级 |
| `internal/splitter/` | macOS (Go) | **流式低延迟断句器** | 4~6 字首句微切分，流式消费中原子剥离 `[ACTION:xxx]` 标签，保证发声文本纯净 |
| `internal/cloud/` | macOS (Go) | **云端 SSE 通信客户端** | HTTP SSE 长连接维护、Token 文本流接收、协程级打断信号派发 |
| `server/` | Linux/Docker (Go) | **轻量云端实时网关 (:8088)** | 承接大模型流式调用，支持 `context.WithCancel` 协程级中止与 Token 截断 |
| `android/` | Android (Kotlin + NDK) | **Pixel 原生移动端宿主** | Material 3 界面、11 状态严密状态机、前台服务（Foreground Service）、JNI 桥接 |
| `cmd/avatar-asr/` | macOS (Swift) | **原生离线语音识别 CLI** | 基于 `AVAudioEngine` 与系统级 Speech 原生引擎，零 Python 依赖直接输出文本 |

## 四、 对通用 Harness 演进的启示与借鉴

在建设通用 Agent Harness 时，`FastAvatar` 的落地经验提供了重要的系统工程启示：

1. **“线束税”在端侧是生死线**：在云端多花 1000 个 Token 做 Prompt 装配影响的只是几厘钱；而在端侧，任何厚重的胶水层和多余的内存拷贝都会直接导致手机发热限频或触发 OOM 强杀。
2. **纯文本流上行/下行是最佳性价比架构**：避免在端云之间传输高开销的裸音频流或 WebRTC 音视频通道，端侧做 ASR/TTS、端云纯传 Token 文本，是在实时性、带宽成本与隐私保护之间最均衡的工业解。
3. **动作元语与表现层彻底解耦**：核心库（C++）绝对不应该感知业务角色名称、UI 皮肤或动效网格，核心 Harness 仅输出标准枚举动作元语（如 `ActionType::SIT`、`MotionVector`），表现层（Compose / Wails Canvas）作为纯粹的事件消费者进行渲染。
